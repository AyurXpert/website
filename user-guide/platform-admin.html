1. Overview

This guide covers subscription.html — the single page a platform admin uses to manage every tenant's plan, billing, NCISM capacity requests, and the platform-wide pricing/GST configuration that every tenant sees.

1.1 Who Is Platform Admin

The platform_admin role is separate from every tenant's own staff roles (super_admin, dept_admin, etc.) — it is the AyurXpert company's own account, not owned by any hospital tenant. On login it lands directly on subscription.html and is gated by the is_platform_admin boolean on the profiles table (checked live on every page load, never cached).

Only one platform_admin account should normally exist As of this writing there is exactly one: admin@ayurxpert.com. If a second one is ever created, both would see and manage the same tenant-wide data — there's no per-admin scoping.

2. All Tenants Tab

The default tab on subscription.html. Lists every tenant on the platform with their plan, billing status, and usage.

2.1 Summary Stats

Five cards at the top of the page: Total Tenants, On Trial, Active Paid, Expiring ≤30d, Expired. These recompute from the same tenant list shown below — they are not separately cached.

2.2 Search & Filter

Filter the tenant table by organisation name (text search), subscription status, or plan type. Filters combine with AND logic — e.g. status=Expiring + plan=Growth shows only Growth-plan tenants that are expiring.

2.3 Editing a Tenant's Subscription

Click ✏ Edit on any tenant row to open the Edit Subscription modal. This is the only place a platform admin directly changes a tenant's billing state.

FieldWhat It Controls

2.4 Expiring / Expired Tenants

The tenant table automatically sorts Expired tenants first, then Expiring tenants (soonest first), then everyone else alphabetically — so tenants needing attention are always visible at the top without needing to apply a filter. Expired/expiring rows also get a light red/amber background tint.

3. NCISM Requests Tab

Teaching Hospital / College tenants submit a capacity request from their own admin.html Subscription tab (new UG intake tier and/or PG department seats). Every pending request appears here for review.

  1. 1
    Review the request — organisation name, current vs. requested UG intake, requested PG department additions, and the computed fee (including its GST breakdown, frozen at the rate that applied when the tenant submitted).
  2. 2
    ✓ Approve — confirms, then immediately runs platform_approve_ncism_request(): seeds OPDs/departments/beds on a tenant's very first activation, or adds only the positive bed/seat delta on a later upgrade (never removes existing beds).
  3. 3
    ✗ Reject — prompts for an optional reason, marks the request rejected. No data changes on the tenant.
Approval is immediate and irreversible via the UI There is no "undo approve" button. If a request was approved by mistake, the tenant's OPDs/departments/beds must be corrected manually (or via a fresh SQL fix) — there's no automated rollback path.

4. Pricing Tab

Every ₹ figure a tenant ever sees anywhere in the app — NCISM capacity fees, and (once set) the SaaS subscription plan fees — is configured from this one tab. Nothing here is hardcoded in the app's code.

4.1 GST Rate

A single platform-wide GST percentage, applied on top of every fee shown anywhere (NCISM tiers, PG seat fee, SaaS plan pricing). It is intentionally a single editable number rather than hardcoded, since the government rate changes from time to time. Changing it here immediately changes the "+GST Total" figures shown across this page, the tenant's own NCISM Capacity Plan card, and their Current Plan card — nothing needs to be redeployed.

GST is calculated, not stored, on most fee displays Only NCISM capacity requests freeze the GST rate/amount that applied at submission time (for audit correctness — a later rate change shouldn't silently rewrite a pending or historical request's fee). Every other fee display (tiers, PG seat fee, plan pricing) recomputes live from the current rate.

4.2 UG Intake Tiers

The fixed set of UG intake sizes (currently 60 / 100 / 150 / 200 students/year) a Teaching Hospital/College can choose between, each with its own one-time capacity-activation fee. Edit a tier's fee, or Deactivate a tier to hide it from tenants without deleting its history. "+ Add Tier" creates a new intake size if the institution needs one not already listed.

4.3 PG Seat Fee

A single per-seat fee applied to every PG department seat a tenant requests, regardless of department. There is only one PG seat fee for the whole platform (not one per department).

4.4 SaaS Plan Pricing

Independent monthly and annual fees for the Starter, Growth, and Enterprise plans. Free Trial has no pricing row — it is always ₹0 and has no billing cycle.

Annual is not auto-discounted from monthly Enter the actual annual figure you want to charge — the system does not compute it as "monthly × 12 minus a discount." This was a deliberate choice for flexibility.

Each plan row has its own Save button — editing Starter's monthly fee does not affect Growth or Enterprise, and editing monthly does not affect annual.

5. Common Scenarios

A. A tenant's trial is about to expire and they've decided to subscribe

  1. 1
    Go to All Tenants, find the tenant, click ✏ Edit.
  2. 2
    Set Plan to Starter/Growth/Enterprise, set Billing Cycle to Monthly or Annual, set Status to "Active (Paid)".
  3. 3
    Set Subscription Expiry to one month or one year out (matching the billing cycle you chose).
  4. 4
    Save. The tenant's own dashboard immediately shows their new plan, billing cycle, and fee (with GST) on next load.

B. A Teaching Hospital wants to increase their UG intake mid-year

No action needed from the platform admin until the tenant submits a request themselves from their own Subscription tab. Once submitted, review and approve it from the NCISM Requests tab (Section 3).

C. The government changes the GST rate

Go to Pricing → GST Rate, update the number, click Save. Every fee display across the platform (this page and every tenant's dashboard) reflects the new rate immediately — no other changes needed.

6. Troubleshooting

I saved a fee and got a success message, but the old value is still showing As of Session 89, every pricing save (GST rate, tiers, tier activation, PG seat fee, plan pricing) explicitly checks that a row was actually returned after saving. If you now see a real error message like "Save did not apply — no matching row", that's a genuine permissions/data problem — check that your account still has is_platform_admin = true. If you still see a false "success" with no change, try a hard refresh (Ctrl+Shift+R) first — a stale cached copy of the page's JavaScript is the most common cause.
A change I just made isn't visible on the live site yet The live ayurxpert.com site is a separate deploy from the app's source — every change needs to be synced and pushed before it's visible, and Cloudflare's CDN cache can take a minute or two to catch up even after that. Hard-refresh (Ctrl+Shift+R) before assuming something is broken.

8. ABDM Multi-Tenant Bridge Architecture & Data Security

Written for answering ABDM/NHA reviewer questions on how one AyurXpert platform serves many hospital tenants through a single ABDM Bridge registration, and how one tenant's health data is kept from ever being visible to another. Every claim below was directly verified against the live production database and Edge Function source on 8 Aug 2026 (Session 158) — not written from memory. If asked for proof during a real ABDM review, every mechanism described here can be demonstrated live.

This is an internal technical reference, not a polished external answer Adapt the wording before sending anything verbatim to ABDM/NHA or an auditor. The substance is accurate as of the verification date above — re-verify anything load-bearing before quoting it if significant time has passed, the same way every other section of this guide should be treated.

8.1 The Bridge Model — One Certification, Many Facilities

AyurXpert is registered with NHA as a single ABDM Bridge System (Sandbox ID SBXID_033899) — not as an individual Health Information Provider/User (HIP/HIU) per hospital. This is the standard, NHA-sanctioned architecture for a multi-tenant HMS vendor: one Bridge certification (WASA + FT security assessment, M1/M2/M3 functional testing) covers every tenant on the platform, rather than requiring each hospital to independently certify.

Two distinct identities are involved, and they scale differently:

IdentityScopeSet once, or per tenant?
Bridge registration (SBXID_033899, Client ID/Secret)Platform-wide — AyurXpert Technologies as a companyOnce, ever. Never re-done per tenant.
HFR Facility ID (e.g. IN2910002132)One specific hospital's real government registration in India's Health Facility RegistryOnce per tenant, self-service since Session 158 (admin.html → ABDM Bridge Configuration)

A tenant hospital never needs its own ABDM certification, its own WASA/FT audit, or its own NHA demo — those are all satisfied once, at the platform level. What each tenant DOES still need is its own Facility ID, covered next.

8.2 Facility Registration — Two Required Steps

Having a Facility ID recorded in AyurXpert's own database is not sufficient by itself — ABDM's own systems must independently be told that Facility ID belongs to AyurXpert's Bridge. Both steps are required, and both happen from admin.html → ABDM Bridge Configuration (super_admin only, dept_admin sees it read-only):

  1. 1
    Government HFR registration — the hospital's own admin registers at facility.abdm.gov.in using the hospital's PAN/license details (AyurXpert cannot do this on a tenant's behalf — it is the hospital's own legal registration). "Submitted" status is sufficient to proceed; full NHA validation is not required for the facility to function (confirmed live: Srishti Ayurveda's IN2910002132 has worked in production since "Submitted" status, has never reached "Validated").
  2. 2
    Bridge-service registration — the resulting Facility ID is registered as a HIP+HIU service under AyurXpert's own Bridge via ABDM's MutipleHRPAddUpdateServices API (register_hip_service action, abdm-auth Edge Function). Without this second step, ABDM's servers do not recognize the Facility ID as part of AyurXpert's Bridge at all, regardless of what AyurXpert's own database says.
Both steps are one click "Save & Register with ABDM" on the panel does both in sequence — saves locally, then calls ABDM's live API. Live-verified against the real ABDM sandbox (registration succeeded, independently re-confirmed via "Check Bridge Services" that ABDM's own systems list the facility as an Active HIP+HIU service).

8.3 How One Shared Webhook Reaches the Right Tenant

Every ABDM callback — for every tenant, for every flow (Scan & Share, consent, data-flow) — arrives at the same single URL: https://xvlvifiebafvgzlixdee.supabase.co/functions/v1/abdm-webhook. ABDM does not know or care that this URL serves multiple hospitals; from ABDM's side, each Facility ID is a distinct, independently-addressable participant.

The webhook resolves which tenant a given inbound request belongs to by reading the X-HIU-ID or X-HIP-ID header ABDM itself sends on every callback, and matching it against tenants.abdm_hiu_id / tenants.hfr_id:

// supabase/functions/abdm-webhook/index.ts
if (hiuHeaderId) {
  tenantId = (SELECT id FROM tenants WHERE abdm_hiu_id = hiuHeaderId).id;
}
if (!tenantId && hipHeaderId) {
  tenantId = (SELECT id FROM tenants WHERE hfr_id = hipHeaderId OR abdm_hiu_id = hipHeaderId).id;
}
// every subsequent read/write in this request is explicitly scoped to that tenantId
This routing is only as safe as the ID mapping is 1:1 — found and fixed 8 Aug 2026 Until Session 158, nothing in the database prevented two different tenants from ending up with the same hfr_id/abdm_hiu_id — which would have made this exact lookup ambiguous or wrong, silently misrouting one tenant's ABDM traffic to another. Confirmed live that no existing tenant collided, then added partial unique indexes (tenants_hfr_id_unique, tenants_abdm_hiu_id_unique — NULLs allowed, since most tenants haven't registered yet) plus a proactive conflict check inside update_tenant_abdm_facility() that rejects a save with a clear message rather than allowing a silent collision. Live-verified: attempted to overwrite WASA1631's Facility ID with Srishti's real registered ID, got a clean rejection naming the conflicting organisation, confirmed via direct query that nothing was actually changed.

8.4 Tenant Data Isolation — Enforced by the Database, Not by Application Code

AyurXpert runs a single shared Postgres database (via Supabase) for every tenant — not a separate database per hospital. This is a deliberate, standard multi-tenant SaaS architecture, and the isolation guarantee comes from Postgres Row Level Security (RLS), enforced by the database engine itself on every single query — not by trusting application/frontend code to filter correctly.

The pattern, identical across every clinical and ABDM-related table:

-- Applied to patients, visits, abdm_consents, hiu_consent_requests,
-- hiu_received_records, link_tokens, audit_logs, and more
USING (tenant_id = (
  SELECT profiles.tenant_id FROM profiles WHERE profiles.id = auth.uid()
))

auth.uid() is the caller's own verified identity from their Supabase Auth session (JWT) — not something a request can spoof. A staff member logged in as Hospital A can only ever have Postgres return rows whose tenant_id matches Hospital A's own tenant — for every query, including ones a future bug in AyurXpert's own JavaScript might accidentally construct without a tenant filter. The database refuses the row regardless.

TableContainsRLS status (verified live, 8 Aug 2026)
patients / visitsPatient records, clinical visitstenant-scoped SELECT/UPDATE via profiles.tenant_id
abdm_consentsHIP-side consent statetenant-scoped, ALL commands
hiu_consent_requestsOutbound consent requests + encryption key materialtenant-scoped, ALL commands
hiu_received_recordsActual pulled external patient health data (M3 flow)tenant-scoped, ALL commands
link_tokensHIP-init/User-init linking tokenstenant-scoped, ALL commands

abdm_callbacksRaw inbound ABDM webhook payloads (pre-routing)service_role only — zero access for any tenant's own staff, any role, under any circumstance
The Bridge webhook itself is the one deliberate exception, and it's tightly scoped ABDM's inbound callbacks arrive with no AyurXpert user session at all (there's no logged-in "user" — it's a machine-to-machine call from ABDM), so abdm-webhook necessarily uses Supabase's service-role key, which bypasses RLS by design. Isolation there is enforced by explicit code instead: resolve exactly one tenantId from ABDM's own header (§8.3), then scope every operation to it — not by RLS. This is why the uniqueness fix in §8.3 mattered: it's the one place in the whole system where isolation depends on a mapping being correct rather than a database constraint being unbypassable.

8.5 Encryption of Health Data In Transit

Actual clinical data exchanged with ABDM (the FHIR bundles pushed during a Pull Records/M2 flow, or fetched during an M3 HIU consent flow) is encrypted end-to-end using ABDM's own mandated scheme (Fidelius-compatible), independent of and in addition to standard HTTPS/TLS transport encryption:

  • ECDH key exchange (Curve25519, expressed as a short Weierstrass curve to match ABDM's real wire format)
  • AES-256 key derived via HKDF-SHA256 from the ECDH shared secret
  • Payload encrypted with AES-256-GCM (authenticated encryption)

Confirmed working against the real ABDM sandbox, not just locally reasoned about — 3 independent successful Pull Records round trips (6–7 Aug 2026), each completing in 3–8 seconds end-to-end.

8.6 Consent-Gated Access — Not an AyurXpert Policy, an ABDM-Enforced One

AyurXpert cannot request another facility's data for a patient without that patient explicitly granting consent through ABDM's own consent-manager flow (approved on the patient's ABHA/PHR app, not inside AyurXpert). Confirmed end-to-end, live: consent request raised → patient grants on their own app → data fetched only after grant → consent revoke actually deletes AyurXpert's locally-stored copy of that data server-side, not just a status flag — genuine ABDM data-erasure compliance, verified 7 Aug 2026.

8.7 Credential & Secret Management

The Bridge's Client ID and Client Secret exist only as Supabase Edge Function environment secrets — set once via supabase secrets set, read server-side inside Edge Functions, and never included in any response sent to a browser, for any tenant, any role. No tenant's staff — including a super_admin — can retrieve these credentials through the application, because the application never has them client-side to begin with.

8.8 Audit Logging & Traceability

Every significant staff action is logged to audit_logs (tenant_id, user_id, action, affected table/record, timestamp) — 1,191+ entries and actively growing at time of writing. The table's own RLS only permits INSERT and SELECT, with no UPDATE or DELETE policy at all — once written, an entry cannot be altered or removed through the application by anyone, including the account that created it.

8.9 Anticipated ABDM/NHA Questions

Q: How does one Bridge serve multiple, unrelated hospitals?

A: The Bridge certification (SBXID_033899) is AyurXpert Technologies' own — it authenticates AyurXpert as a legitimate platform to ABDM. Each hospital using the platform is separately identified to ABDM by its own government-issued HFR Facility ID, registered as a distinct service under that one Bridge. See §8.1–8.2.

Q: If two hospitals share infrastructure, how do you guarantee Hospital A never sees Hospital B's patient data?

A: Enforced at the database engine level via Postgres Row Level Security, not by application code — every query is automatically filtered to the caller's own tenant_id, derived from their authenticated session, and this cannot be bypassed by a bug in AyurXpert's own frontend code. See §8.4.

Q: How does an inbound ABDM callback get routed to the correct hospital, given one shared webhook URL?

A: By the Facility ID ABDM itself sends in the request header, matched against a database-enforced-unique mapping. See §8.3.

Q: Is patient health data encrypted, or just access-controlled?

A: Both. Data exchanged with ABDM is end-to-end encrypted per ABDM's own Fidelius-compatible scheme (§8.5), independent of standard TLS. At rest, data sits in Supabase's managed Postgres infrastructure, which provides standard cloud-provider disk-level encryption; access to any given row is additionally gated by RLS regardless of encryption. (If a formal attestation of encryption-at-rest is needed for a specific audit, confirm the exact wording from Supabase's own compliance documentation/DPA rather than this guide — that's infrastructure-vendor territory, not something re-verified in this session.)

Q: Can a hospital's own staff pull another hospital's patient's data by mistake?

A: No — RLS scopes every read to the staff member's own tenant, and ABDM's own consent framework additionally requires that specific patient's explicit consent grant before any cross-facility data request can even be raised. Two independent gates, not one.

Q: Who can change which Facility ID a hospital is registered under?

A: Only that hospital's own Super Admin (role-gated both client-side and inside the server-side RPC, which independently re-derives the caller's own tenant — never trusts a client-supplied tenant identity).

Q: What happens when a patient revokes consent?

A: AyurXpert's locally-stored copy of that patient's pulled records is deleted server-side, not just hidden — verified live, 7 Aug 2026. See §8.6.

Q: Is there an audit trail of who accessed or changed what?

A: Yes — every action is logged with who, what, when, and which tenant, and the log itself cannot be edited or deleted through the application once written. See §8.8.
